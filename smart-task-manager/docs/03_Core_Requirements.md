# Core Requirements Document
## Smart Task Manager

This document lists exactly what the application must do (functional requirements) and how well it must do it (non-functional requirements), plus the exact technical stack.

---

## 1. Functional Requirements

| ID | Requirement | Acceptance Criteria |
|---|---|---|
| FR-1 | Create a task | Submitting the form with a valid title, priority, and status creates a new task and it appears in the list immediately, without a page reload. |
| FR-2 | View all tasks | Loading the dashboard shows every task as a card, including title, description, priority, status, and deadline. |
| FR-3 | View a single task | Requesting a task by its id returns that task's full details, or a clear 404 if it doesn't exist. |
| FR-4 | Update a task | Editing a task and saving updates only the changed fields and reflects the change on screen immediately. |
| FR-5 | Delete a task | Deleting a task (after confirmation) removes it from the list and the database permanently. |
| FR-6 | Search tasks | Typing in the search box filters the visible tasks to ones whose title or description contains the typed text (case-insensitive). |
| FR-7 | Filter tasks | Selecting a priority and/or status filters the visible list to matching tasks only. Filters can be combined with search. |
| FR-8 | View statistics | The stats panel always shows the current total, count by status, and count by priority, and updates after every create/update/delete. |
| FR-9 | Validate input | Blank titles, titles under 3 characters, and invalid priority/status values are rejected with a specific, readable error message — never a silent failure or generic crash. |
| FR-10 | Handle errors gracefully | Requests for missing tasks return 404 with a message; unexpected server issues return 500 with a generic safe message (never raw stack traces to the browser). |
| FR-11 | Explore the API directly | The interactive Swagger docs at `/docs` list every endpoint, its expected input, and its possible responses, and can be used to test the API without the frontend. |

## 2. Non-Functional Requirements

| Category | Requirement |
|---|---|
| Usability | The UI must be understandable without instructions — labeled fields, visible buttons, clear badges for priority/status. |
| Readability (code) | Every file has a top-of-file docstring explaining its purpose in plain English. Function and variable names describe what they do. |
| Performance | Typical requests (create/read/update/delete/search on a small dataset) should respond in well under 200ms on a local machine. |
| Reliability | The server must not crash on bad input, missing records, or unexpected values — it must return a proper HTTP error instead. |
| Maintainability | Each concern lives in its own file (routing, validation, database access, business rules) so a change in one doesn't require touching the others. |
| Portability | The project must run on any machine with Python 3.10+ and a modern browser — no OS-specific code, no paid services required. |
| Offline-friendliness | The frontend uses no external CDN fonts or scripts, so it renders correctly even without internet access (only the API calls need the local backend running). |

## 3. Technical Requirements (Stack)

| Layer | Technology | Version / Notes |
|---|---|---|
| Backend language | Python | 3.10+ |
| Backend framework | FastAPI | Latest stable (0.110+) |
| ASGI server | Uvicorn | with `--reload` for development |
| Data validation | Pydantic | v2 (built into FastAPI) |
| ORM | SQLAlchemy | 2.x |
| Database | SQLite | single file, `tasks.db` |
| Frontend | HTML5, CSS3, vanilla JavaScript (ES2017+) | no frameworks, no bundler |
| Frontend dev server | VS Code "Live Server" extension | serves static files on `localhost:5500` |
| API docs | Swagger UI / ReDoc | auto-generated by FastAPI at `/docs` and `/redoc` |
| Editor | Visual Studio Code | with Python extension |

## 5. Definition of Done

A feature is considered "done" only when:

1. It works correctly through the Swagger UI (`/docs`).
2. It works correctly through the actual frontend UI.
3. Invalid input is rejected with a clear message, not a crash.
4. The relevant file(s) have comments explaining what was added and why.
5. It has been demoed live, end to end, in front of students.
